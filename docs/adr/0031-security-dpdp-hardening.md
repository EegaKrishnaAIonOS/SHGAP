# ADR-0031: Security & DPDP compliance hardening

- **Status:** Accepted
- **Date:** 2026-07-29
- **Sprint:** Sprint 5 (T22)

## Context

T22 opens Sprint 5 — "High" complexity, 4 person-days, depending only on T05 (Core API + Auth/RBAC). Its five bullets are broad by design: consent capture/withdrawal/privacy notices, encryption at rest + PII field encryption, tamper-evident audit + access logging, a right-to-erasure/data-access workflow, and an OWASP/rate-limiting/dependency/secrets hardening pass. ADR-0015 (Sprint 0) already named the intended stack (pgcrypto/KMS, tamper-evident audit, OWASP ZAP, Snyk) and explicitly flagged that the real implementation effort was deferred to this exact task.

Before writing any code, reading the schema confirmed the DB-level scaffolding already existed but nothing read or wrote it: `ConsentPurpose`/`Consent` (T02) had zero real capture/withdrawal logic anywhere in core-api; `AuditLog`'s own model comment already said "tamper-evidence (hash chaining) is added in T22"; no pgcrypto extension was declared; no encryption, rate limiting, or access logging existed at all.

## Decision

**Consent is append-only, not update-in-place.** Every grant or withdrawal is a new `Consent` row, not a mutation of an existing one — so a person's full consent history (grant → withdraw → re-grant) stays reconstructable, and DPDP's "notice must accompany consent" requirement is met literally: each grant is stamped with the exact privacy-notice `version` shown at the time (`PRIVACY_NOTICES`, one real, purpose-specific notice per `ConsentPurpose`, versioned so a later reword never silently reinterprets an old consent). `POST /consent/:purpose/withdraw` is idempotent by design — withdrawing something never granted, or already withdrawn, is a no-op, not an error, because DPDP requires withdrawal to be as easy as consent.

**Real enforcement, on a real, already-built flow — not a fabricated integration point.** `ConsentService.hasActiveConsent()` gates T21's GeM tender-opportunity alerts: a match is still recorded and logged, but the actual notification only reaches SHG contacts with active `MARKETING_NOTIFICATIONS` consent. This was chosen deliberately over inventing a new consent-checked flow, because it's a real dispatch call this platform already makes.

**PII encryption uses pgcrypto with ciphertext stored as base64 text, not a `bytea` column type change.** `PiiEncryptionService` wraps `pgp_sym_encrypt`/`pgp_sym_decrypt`, applied to `Shg.bankAccountNumber`/`bankIfsc` — the platform's most sensitive existing PII. Keeping the Prisma column type as `String?` (holding base64 ciphertext instead of plaintext) avoided a riskier column-type migration on a table with real data. Pre-T22 seed rows are real, unencrypted plaintext — there was no encrypt path before now and no migration-time key to safely bulk re-encrypt them with — so `decrypt()` falls back to returning the stored value unchanged when it doesn't parse as this service's own ciphertext, rather than throwing on every legacy row. A real rollout would run a one-time backfill through `encrypt()` once a real KMS key exists.

**No real KMS account exists for this pilot** (the same gap ADR-0030 already documented for ONDC's signing key) — `KmsKeyProvider` is a DI-swappable interface; `EnvKmsKeyProvider` reads `PII_ENCRYPTION_KEY` from env when set, or generates a random ephemeral key at boot otherwise (logged loudly, since anything encrypted that run becomes undecryptable after a restart). Swapping in a real KMS-backed provider later is a one-file change.

**Tamper-evidence is a real, verifiable hash chain, not a stored "verified" flag.** Each `AuditLog` row's `hash` covers its own fields plus the previous row's `hash`; `AuditService.verifyChain()` walks the whole table and recomputes every hash, returning exactly where a mismatch starts rather than asserting trust. Both the write-time and verify-time hash inputs run through a recursive key-sorting canonicalizer, because Postgres's JSONB storage doesn't guarantee preserving a JSON value's original key order — without that, a row could fail verification for reasons that have nothing to do with tampering. Known, documented (not hidden) limitation: `record()` reads the last hash and inserts in two separate steps, so two audit writes racing at the same instant could both link to the same previous hash — an acceptable gap at this POC's real write volume, and one `verifyChain()` would actually surface, not silently miss.

**`AuditInterceptor` is opt-in per route (`@Audited('EntityType')`), not a global auto-logger.** A fully generic interceptor guessing at entity id/state from every possible response shape in the app would be either too noisy or too inaccurate; explicit per-route marking mirrors this codebase's existing `@Public()`/`@Roles()` convention. Applied today to the real create/update/delete paths for `Shg` and `Buyer`, and `GemOpportunity` creation — the platform's clearest sensitive-mutation surfaces — not to every controller in the app. A separate `AccessLogMiddleware` logs every HTTP request (method/path/status/duration/actor) regardless of `@Audited` — a distinct, lower-fidelity operational log, not a tamper-evident record.

**Right-to-erasure anonymizes; it does not hard-delete.** `Shg.contactUserId` is a required FK — a real SHG still legitimately references the erased user's row, so `requestErasure()` nulls `name`/`email`, replaces `phone` with a random non-identifying placeholder, and sets a new `UserStatus.ERASED`, withdrawing every active consent along the way. It does **not** touch that user's SHG's own sales/product/registration records — DPDP's legitimate-business/legal-retention exception covers real past transactions, and the response explicitly lists what was retained (`retainedRecords`) rather than silently keeping it unmentioned. Right-to-access (`GET /users/me/data-export`) returns a real, complete export — including bank details genuinely decrypted, since this is the data subject requesting their own data, not a third party.

**Hardening: `helmet()` (standard header baseline), `@nestjs/throttler` as a second, general rate-limit layer** (100 req/min/IP) **on top of — not replacing — OTP's existing purpose-built per-phone-number limiter**, and a full repo secrets audit (no tracked `.env` beyond `.env.example`, no hardcoded high-entropy secret-like literals found via a targeted grep). `npm audit` (the closest real substitute for Snyk available in this environment — no Snyk API token exists here) found and fixed one non-breaking transitive vulnerability; 19 remaining production-dependency findings need a major-version framework bump (NestJS 10→11, react-router 6→7, etc.) genuinely out of scope for a 4-person-day security task — listed honestly below, not silently left off this document.

## Real findings from verification

- `pgcrypto` extension installed and round-tripped for real (`pgp_sym_encrypt`/`pgp_sym_decrypt` verified directly via `psql` before any application code was written).
- The tamper-evidence mechanism was verified to actually detect tampering, not just assert it: a test directly mutates a historical row's `afterState` after the fact, and `verifyChain()` correctly reports the exact row the chain breaks at.
- **`npm audit --omit=dev` on production dependencies found 19 real, currently-open vulnerabilities** (0 critical, 8 high, moderate the rest) concentrated in `@nestjs/*` (10→11 major bump needed), `react-router`/`react-router-dom` (6→7), and `xlsx` (no fix available — already accepted in ADR-0028's own T19 write-up, since this app only ever generates `.xlsx` files, never parses untrusted ones, so the actual exploitable ReDoS/prototype-pollution vectors don't apply). One non-breaking fix (a transitive `uuid`/other dependency) was applied via `npm audit fix`. The rest are a real, tracked gap for a dedicated framework-upgrade pass — not attempted here, since a NestJS or React Router major bump touching every module in the app is its own multi-day migration, disproportionate to fold into this task.
- **No live OWASP ZAP dynamic scan was run** — ZAP scans a live deployed target over HTTP; there is no long-lived deployed environment for this pilot to point it at yet (that's T24's scope). What's real here instead: a manual OWASP Top-10-shaped code review (parameterized queries/Prisma throughout, no raw string SQL concatenation anywhere in this codebase, global `ValidationPipe` with `whitelist`/`forbidNonWhitelisted` already in place since earlier sprints, RBAC guards on every sensitive route, now `helmet()` + rate limiting added) plus the dependency/secrets audits above.

## Alternatives Considered

- **Changing `Shg.bankAccountNumber`/`bankIfsc` to a `Bytes` column** — rejected; storing base64 ciphertext in the existing `String?` column avoids a riskier type-changing migration on a table with real data, for the same practical effect.
- **Bulk-encrypting existing legacy plaintext rows in the migration itself** — rejected; would require hardcoding a real encryption key into a committed SQL file, which is a worse security practice than the honest "legacy rows stay plaintext until backfilled with a real KMS key" gap this ADR documents instead.
- **A fully global, always-on `AuditInterceptor`** — rejected; without an explicit per-route entity type, it can't reliably know what to log for arbitrary responses, and would either miss real mutations or log noise for read-only routes.
- **Relaxing `Shg.contactUserId` to nullable to allow hard-deleting an erased user** — rejected for the same reason ADR-0030 rejected it for MEPMA sync: a much larger, riskier schema change than this task calls for.
- **Attempting the full `npm audit fix --force` major-version bump** to clear every remaining finding — rejected; breaking-change framework upgrades across the whole app are a separate, dedicated migration effort, not something to fold into a security-hardening pass without its own review.

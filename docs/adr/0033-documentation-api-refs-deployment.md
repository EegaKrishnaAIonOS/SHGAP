# ADR-0033: Technical documentation, API references, and a verified (not applied) production deployment

- **Status:** Accepted
- **Date:** 2026-08-04
- **Sprint:** Sprint 5 (T24 — final task)

## Context

T24 closes the sprint plan: technical documentation (architecture, data model, ML model cards, runbooks), OpenAPI/Swagger for every service, a step-by-step deployment guide, and deployment to a production-like India-region environment with blue/green + rollback, monitoring, alerting, and backups (ADR-0013/ADR-0014's own pre-committed requirements, deferred to this task since T22).

No real cloud account or credentials exist in this environment. Before writing any Terraform, this was confirmed explicitly rather than assumed: the honest choice is between (a) building real, reviewable IaC plus a fully working local rehearsal of the whole stack, clearly distinguishing "verified" from "written but not applied," or (b) attempting to fabricate a live deployment that doesn't exist. (a) is what this ADR documents — the same "state the real gap" pattern this project has followed for every other missing external dependency (ONDC registration, KMS, OWASP ZAP, and others).

## Decision

**Real Prometheus instrumentation on all 4 backend services, not a stub.** `prom-client` (NestJS) / `prometheus-fastapi-instrumentator` (FastAPI) expose `/metrics` on every service; `/health` stays a plain liveness probe, and a new `/health/ready` on each service checks its actual hard dependencies (Postgres for core-api/notification-service/ml-services, Redis for voice-service) and returns a real 503 on failure — the Kubernetes liveness/readiness split this platform never had a reason to make until now that a real orchestrator (K8s, or even just Prometheus's `up` metric) is watching it.

**The k6/Playwright discipline from T23 caught a real defect here too, immediately: `/health` and `/metrics` are both `@SkipThrottle()`'d on core-api** — otherwise the exact throttle T23/ADR-0032 fixed for `/health` would silently break Prometheus scraping under load the same way it broke uptime monitoring before. Not a new bug; the same class of bug, caught this time before it shipped rather than after a load test found it.

**A real, fully working local production-rehearsal, not a diagram.** `infra/docker-compose.apps.yml` containerizes all 5 services (the exact images CI builds) on the same network as the existing dev infra; `infra/docker-compose.monitoring.yml` adds a real Prometheus + Grafana + Loki + Promtail + Alertmanager stack. Every piece was actually started and checked, not assumed: Prometheus's `/targets` showed all 4 services `UP`; a real dashboard query returned real, moving request-rate numbers; Loki actually ingested a real core-api log line via Promtail's Docker-socket discovery; Grafana's provisioned dashboard and both datasources were confirmed via its own API, not just "the container started."

**This rehearsal found and fixed a real, previously-latent bug: the web container's nginx had no reverse-proxy or SPA-routing config at all.** `vite.config.ts`'s own comment had explicitly named "a real deployment would front both with a single reverse proxy the same way" as the intended production setup for `/api`/`/voice-api` — nobody had built it, because nothing had ever run the built container against real backend services until this task did. `apps/web/nginx.conf` is that config; it also fixed a second real bug the same testing pass surfaced — `wget http://localhost/health` failing inside the container because Alpine's resolver returns `::1` for `localhost` before `127.0.0.1`, and nginx only bound the IPv4 listener. Both fixes are real, verified (`curl` through the actual running container, both before showing the failure and after showing success), not inferred.

**Terraform targets AWS `ap-south-1` (Mumbai) as the concrete India-region provider** — a real region, a real, exhaustively-documented Terraform provider, and the module structure (network/database/cache/storage/eks/secrets) is exactly what would need to change providers, not restructure, if a real MeitY-empanelled CSP is mandated later (ADR-0013's own stated reason for choosing Terraform in the first place). One RDS Postgres instance (PostGIS + pgvector as supported extensions, matching ADR-0004's single-engine decision), one ElastiCache Redis node (matching this pilot's real, modest Redis usage — OTP codes, sessions, BullMQ queues, nothing that needs cluster-mode HA to hit the sprint's own uptime target), one EKS cluster with one managed node group sized for blue/green's real headroom need (`max_size = desired + 2`), two S3 buckets (product images, DB backups) with separate lifecycle policies so a retention mistake on one can never touch the other, and Secrets Manager entries pre-filled with the real database/Redis connection strings but every third-party provider credential left blank — the same "provision the container, don't fabricate its contents" rule already used for every other external credential in this platform.

**`terraform validate` and `terraform fmt` were run for real; `terraform apply` was not, because there is nothing to apply it against.** This is stated explicitly rather than left ambiguous — a reviewer should not have to guess whether "Terraform exists" means "a real environment is running."

**Kubernetes: blue/green via two full Deployments per service and a Service-selector patch, not a Deployment-strategy setting.** `core-api-blue`/`core-api-green` (and the same pattern for all 5 services) are both always running — the "inactive" one is where the next release lands and gets smoke-tested _before_ `infra/k8s/scripts/switch-traffic.sh` flips the Service's selector, which is also the rollback: the same script, run in reverse, in seconds, no redeploy. This is literally what ADR-0013 pre-committed to ("harder to roll back cleanly" was its stated reason for rejecting bare-VM hosting) — T24 is where that promise gets built, not invented fresh.

**Kubernetes manifests were validated by rendering, not by applying to a live cluster.** `kubectl kustomize infra/k8s/base/` and `kubectl kustomize infra/k8s/monitoring/` both render cleanly (29 and several more real resources respectively) — this caught two real path mistakes (`namespace.yaml` written to the wrong directory; Kustomize's path-traversal security restriction blocking a cross-directory `configMapGenerator` reuse of the Compose rehearsal's own config files) before they could be silently wrong. `kubectl apply --dry-run=client` was attempted and correctly failed with "no cluster configured" — there is no live cluster in this environment to validate against at that level, and no such cluster was fabricated to make the check pass.

**Monitoring config is duplicated, not shared, between the Compose rehearsal and Kubernetes — a named trade-off, not a silent inconsistency.** Kustomize refuses to read `configMapGenerator` source files from outside its own kustomization root (a real, deliberate security restriction, not a bug worth working around with `--load-restrictor none`). Alert rules, Grafana dashboards/datasources, and Loki's config are copied inline into `infra/k8s/monitoring/*.yaml` rather than generated from `infra/monitoring/*` — real drift risk between the two copies, named in `infra/k8s/monitoring/kustomization.yaml`'s own header comment rather than hidden.

**Backups: a real, tested `pg_dump`/`pg_restore` cycle, run against real local data before writing the runbook that describes it.** `infra/scripts/backup-postgres.sh` produced a real dump of the local dev database; `infra/scripts/restore-postgres.sh` restored it into a fresh `shgap_restore_test` database; row counts (`shg`, `products`, `users`) were compared before and after and matched exactly, then the test database was dropped. This is the actual sequence `docs/runbooks/backup-restore.md` documents — not a procedure written from imagining how `pg_dump` should work. RDS automated snapshots and an in-cluster `CronJob` (uploading to the same S3 bucket the storage module provisions) are the real, unverified-for-the-same-reason-as-everything-else-cloud extensions of this for a live deployment.

**Alerting has a real receiver today, and a named real gap for tomorrow.** No Slack/PagerDuty account exists for this pilot (same rule as every other "no real X" gap this project has documented) — `alertmanager.yml` routes to `alert-log-sink`, a genuine ~30-line Python HTTP server that logs every alert it receives to stdout, verifiable via `docker compose logs alert-log-sink`, not a receiver that silently drops alerts. Four real alert rules fire against metrics that actually exist: `ServiceDown` (`up == 0`), `ResponseTimeSLOBreached` (p95 > 3s — the literal number T23/ADR-0032's k6 load test validated, now watched continuously), `HighErrorRate` (5xx > 5%), and `NotificationDeliveryFailureRateHigh` (>20% failure on the real `notification_jobs_total` counter this task added to `NotificationsProcessor`).

**A CD workflow exists and is real, but is `workflow_dispatch`-only, never `on: push`.** Wiring blue/green deploy automation to fire on every push against `AWS_DEPLOY_ROLE_ARN`/`EKS_CLUSTER_NAME` secrets that don't exist in this repo would mean it fails loudly on every single commit. Manual dispatch, gated behind a GitHub `production` Environment (real approval-gate infrastructure a repo admin configures, not something this workflow file can create for itself), means it only ever runs when a real operator with real cluster access deliberately chooses to run it — and its actual deploy logic calls the exact same `deploy-inactive.sh`/`switch-traffic.sh` scripts a human would run by hand, so there is exactly one blue/green implementation, not two that could drift.

**Notification-service got Swagger from a genuine zero.** core-api's `@nestjs/swagger` setup already existed (T05); notification-service had no `@nestjs/swagger` dependency, no `DocumentBuilder`, nothing — a from-scratch addition, not an extension. ml-services and voice-service (FastAPI) already had auto-generated `/docs` for free; two endpoints with no docstring got one (`categorization`, `scheme-guidance`) since that was a cheap, real improvement; the response-model-typing gap in `market_intelligence`/`forecast`/`matching` was deliberately left alone rather than force a refactor beyond this task's real scope — named honestly in the deployment guide's gap table instead.

## Real findings from verification

- Full local rehearsal: all 5 app services + 4 infra services + 5 monitoring services running simultaneously, all health-checked, Prometheus scraping all 4 real `/metrics` endpoints, Grafana dashboard showing live data, Loki showing real ingested log lines — all confirmed via direct API calls during this task, not assumed from container `Up` status alone.
- Two real bugs found and fixed by that rehearsal: the web container's missing nginx reverse-proxy/SPA config, and its IPv6/`localhost` healthcheck failure (both described above).
- `terraform validate`: clean (one real warning — S3 lifecycle rules needing an explicit `filter {}` block for a newer provider version — found and fixed, not just noted).
- `kubectl kustomize`: both `infra/k8s/base/` and `infra/k8s/monitoring/` render cleanly; two real authoring mistakes (misplaced `namespace.yaml`, the cross-directory `configMapGenerator` restriction) were caught this way before they could reach a real cluster.
- Backup/restore: real data round-tripped correctly (exact row-count match across 3 tables) on the first real attempt.
- `turbo run lint test build`, ruff/pytest for both Python services: clean after every change in this task (see the commit's own CI run).

## Alternatives Considered

- **Fabricating a "successful" `terraform apply`/live cluster** to make this ADR read as more complete — rejected outright; this project's standing rule is to state a real gap, never a fabricated success, and this is the highest-stakes place that rule could be violated (real infrastructure claims a reader might act on).
- **Skipping the local production-rehearsal and only writing IaC** — rejected; an unrun Docker Compose file is exactly as unverified as unapplied Terraform, and the rehearsal is what actually found two real bugs (the nginx gaps) that pure code review of the Dockerfiles would not have surfaced.
- **A managed observability SaaS (Datadog/New Relic) instead of self-hosted Prometheus/Grafana/Loki** — rejected; ADR-0014 already rejected this specifically for India-region data-residency reasons (ADR-0013), and nothing in T24 changes that reasoning.
- **`--load-restrictor none` to let Kustomize's `configMapGenerator` reuse files across directories** — rejected; bypassing a deliberate security restriction to avoid ~150 lines of duplicated YAML is the wrong trade, especially for a mechanism (`kubectl apply -k`) a real operator will run directly, potentially without knowing that flag was ever needed.
- **Building a heavier, multi-AZ-NAT, multi-node-group EKS setup** — rejected for this POC's real scale; ADR-0013 already flagged Kubernetes' own operational overhead as something to mitigate, not maximize, and one NAT gateway / one node group with real HPA headroom is the leaner, real-scale-appropriate choice, named as a real (not hidden) trade-off in `infra/terraform/modules/network`'s own comment.

# ADR-0026: Buyer matching recommender, ranking, and explainability

- **Status:** Accepted
- **Date:** 2026-07-27
- **Sprint:** Sprint 3 (T17)

## Context

T17 is the last Sprint 3 task and the final piece of Module 4 (Buyer Matching Engine): compute product/buyer embeddings, blend content similarity with collaborative signals, score match + expected demand per SHG-buyer pair, re-rank with LightGBM, generate SHAP + template explanations, and serve `GET /recommendations/{shgId}` with accept/reject feedback capture. ADR-0009 (Sprint 0) planned embeddings + pgvector/FAISS + LightFM + LightGBM + SHAP for this; as with ADR-0008/ADR-0024 for forecasting, this plan meets real pilot data at T17 and deviates from it in several concrete, verified ways below.

**The real data constraint that shapes this ADR**: verified directly against the live dev database before designing anything — 4 buyers, 6 products, 0 buyer-linked sales (`sales.buyer_id` is `NULL` on all 1,032 rows), 0 enquiries, 0 recommendations ever made. There is currently no real SHG↔buyer interaction data of any kind, only buyers' static declared category interests (`BuyerCategoryInterest`, 14 rows). A collaborative-filtering signal (LightFM) has nothing real to fit; a learning-to-rank model (LightGBM) has no real labels to train on. Every design decision below follows from taking that seriously rather than fabricating signal that doesn't exist yet.

## Decision

**Embeddings reuse the existing 384-dim sentence-transformer model, not a new 768-dim one.** `Product.embedding`/`Buyer.embedding` were `vector(768)` placeholders since T02, with a schema comment explicitly noting they "anticipate a different, not-yet-built model" (unlike `SchemeChunk.embedding`, correctly `vector(384)` to match the real `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` model already running in ml-services for T08/T12). A second embedding model would double the Docker image's model-download cost and memory footprint for no identified benefit at 6 products / 4 buyers of short catalog-style text — the same model already loaded for categorization is reused, and a new migration corrects both columns to `vector(384)` (verified: both were 100% NULL in every real environment, so this was a safe, data-free type change; the corresponding `ivfflat` indexes were dropped and recreated by hand, since Prisma's schema diff can't see indexes on `Unsupported`-typed columns — the same limitation ADR-0025 already hit).

**Content similarity (cosine, via the embeddings above) is the primary, always-available signal — not LightFM.** `LightFM` was evaluated and **dropped**: with zero real buyer-product interactions, fitting a collaborative model would mean fitting to an empty/absent interaction matrix — memorizing nothing, not learning a real preference. This is not a departure from ADR-0009's own reasoning so much as its logical conclusion: ADR-0009 already rejected _pure_ collaborative filtering for exactly this cold-start reason; T17 finds the pilot is currently at 100% cold-start, so the content-only path IS the correct one today, not a fallback within a hybrid.

**FAISS was not added.** ADR-0009 called it an "optional accelerator" over pgvector; at 6 products, brute-force cosine similarity (plain NumPy dot products on L2-normalized vectors) is trivially fast, and pgvector already provides the ANN infrastructure ADR-0004 chose if the pilot ever needs it at scale.

**Match score is a reasoned heuristic blend today, not a trained model** — `content_similarity` (weight 0.45), `category_interest` (declared `BuyerCategoryInterest`, 1.0/0.0, weight 0.30), `price_band_fit` (product price vs. the buyer's stated `demandProfile.priceBandMin/Max`, weight 0.15), `geo_proximity` (haversine distance, capped at 150km, weight 0.10, defaulting to neutral 0.5 rather than penalizing when either side has no location — a state-level GOVERNMENT_PROCUREMENT buyer often has no district at all). Verified directly against the real seed data: a pickle SHG's recommendations correctly rank an in-district BULK buyer with declared "Pickles" interest highest (0.7793), and an institutional handicrafts buyer with no declared pickle interest lowest (0.2873) — sensible, explainable behavior with zero training data required.

**`expectedDemand` reuses T15's already-trained per-product Prophet demand model** (`demand_model.forecast()`, summed over the next 30 days) rather than inventing a second demand estimate — a deliberate cross-task integration, not just a dependency listed in the sprint plan. Returns `null` honestly (not a fabricated number) for a product without a registered model yet.

**LightGBM re-ranking and SHAP explanations are both real code paths, gated behind a minimum real-feedback threshold** (`min_feedback_rows_for_ranker`, default 30 accept/reject responses across every recommendation ever served) — mirroring T15's exact "decline to train below threshold" pattern for demand/price models. `matching/ranking.py`'s `train()`/`score()` were verified directly against a synthetic accept/reject fixture (LightGBM genuinely separates strong from weak candidates once trained); with 0 real feedback today, `score()` correctly returns `None` and the heuristic weighted score serves as the real, live ranking. **SHAP was deliberately left out of `requirements.txt`**: with no trained ranker yet, there is no model for SHAP to explain, so it isn't needed today — the "SHAP plus human-readable templates" pairing ADR-0009 called for already treats templates as a real, standalone explanation path (not a fallback-only stub), and `matching/explanations.py` generates real, per-recommendation reasons directly from the same computed sub-scores the match score is built from (e.g., "Anantapur Wholesale Foods has expressed interest in Pickles..."; "Priced at ₹150, within this buyer's usual range."). SHAP output can be added alongside these once a real ranker exists to explain.

**`GET /recommendations/{shgId}` is served by core-api, not ml-services** — ml-services exposes `GET /matching/candidates?shg_id=...` (a pure compute endpoint, no persistence, mirroring T14/T15's forecast-router convention), and core-api's `RecommendationsService` calls it, persists results into the real `Recommendation` table, and owns the user-facing API + RBAC. This is the same compute/persist split as `CategorizationService` (T08) — except this is the primary, user-facing feature, not a "hint only" proxy, so an unreachable ml-services surfaces as a clear `503 ServiceUnavailableException`, not a silently empty list. Reads/writes are ownership-scoped (the recommended SHG's own contact user, or admin) via the same `contactUserId` check `shgs`/`products` already use — a `Recommendation` belongs to a specific SHG, unlike the buyer registry's admin-curated model (ADR-0025).

**A refresh only touches still-`PENDING` recommendations** for a given (SHG, buyer) pair — one already `ACCEPTED`/`REJECTED` is a real historical decision and must be neither overwritten nor duplicated by a later recompute.

## Real bugs found and fixed during verification

- **`libgomp.so.1: cannot open shared object file`** — the ml-services Docker container (Debian `python:3.11-slim`) crashed on boot importing `lightgbm`, whose Linux wheel dynamically links against the system OpenMP runtime rather than bundling it (a well-known LightGBM/slim-image packaging interaction). Fixed by adding `apt-get install -y libgomp1` to the Dockerfile; verified by a real container boot before and after.
- **Duplicate recommendations on refresh**: the original refresh logic looked for an existing row with `status: 'PENDING'` to decide update-vs-create, but for a buyer whose recommendation had already been `ACCEPTED`, that query correctly found nothing _PENDING_ — and so incorrectly created a brand-new `PENDING` row for the same buyer, leaving two rows (one real decision, one spurious duplicate) where there should be one. Caught by literally re-fetching `GET /recommendations/:shgId` twice against the real database and noticing 5 rows for 4 buyers. Fixed by checking for _any_ existing row for that (SHG, buyer) pair regardless of status, and skipping entirely (no update, no create) when one exists and isn't `PENDING`.

## Alternatives Considered

- **LightFM now, hoping it degrades gracefully with no data** — rejected; a model "trained" on zero real interactions isn't a safety net, it's a source of misleadingly confident-looking output for a metric (match score) officials and SHGs are meant to trust. Better to be a well-reasoned heuristic today and a real hybrid once interaction data exists (real sales with `buyer_id` populated, or real enquiries).
- **A second, purpose-built embedding model for buyer/product matching** — rejected (see Decision); no identified benefit at this data scale over reusing the model already resident in the service.
- **Serving `/recommendations/{shgId}` directly from ml-services** — rejected; recommendations are user-facing, RBAC-relevant, ownership-scoped records (`Recommendation.shgId`), which is core-api's existing responsibility (auth, guards, Prisma) — ml-services has no auth layer today and shouldn't grow one just for this endpoint.
- **Fabricating SHAP output against the heuristic score directly** (treating the weighted-sum formula itself as a "model" to explain) — rejected; SHAP explains trained models' learned feature attributions, and applying it to a fixed linear formula whose weights were chosen by hand adds a veneer of statistical rigor the number doesn't actually have. Plain templates built from the same real sub-scores are more honest about what's actually being shown.

## Consequences

- Positive: the full path — embedding computation/storage, content-similarity scoring, heuristic match + real T15 demand-forecast integration, template explanations, ml-services↔core-api persistence, ownership-scoped RBAC, and accept/reject feedback capture — was verified end-to-end against the real 3-SHG/4-buyer/6-product dataset, through a real Docker boot of both services on the shared network, not just unit-mocked. Two real bugs (a missing system library, a duplicate-write race in the refresh logic) were found and fixed by actually exercising the code, not assumed away.
- Trade-offs: today's match scores are a reasoned heuristic, not a learned model — they will not improve on their own the way a trained ranker would as more data arrives. This is intentional and self-correcting: `POST /matching/train-ranker` (and the same weekly scheduled job that already retrains T15's demand/price models) will begin producing a real LightGBM ranker automatically once 30+ real accept/reject responses accumulate through the very UI this task built — the honest heuristic is a bridge, not a permanent ceiling.
- Deferred, not abandoned: LightFM (needs real buyer-product interaction volume — real sales with populated `buyer_id`, or real enquiries, neither of which exist yet), FAISS (needs a product/buyer count where brute-force cosine similarity stops being trivially fast), and SHAP (needs a real trained ranker to explain) are all real, planned next steps once their respective data preconditions are met, not permanently rejected technologies.

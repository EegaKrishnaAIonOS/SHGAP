# ADR-0032: Stabilization — load test, E2E automation, voice-accuracy holdout re-validation, and identity-keyed throttling

- **Status:** Accepted
- **Date:** 2026-07-31
- **Sprint:** Sprint 5 (T23)

## Context

T23 opens the "Testing & Stabilization" sprint: load-test the `<3s avg response`/`>=99% uptime` targets (k6/Locust), run automated E2E tests across every module (Playwright), re-validate `>=90%` Telugu voice accuracy on a holdout set, and triage defects to zero open P0/P1. Depends on T19-T21 (the dashboards, admin portal, and external integrations Playwright now exercises).

No browser-automation tool existed for T19-T22, so every UI change in those tasks was verified only by hand — an explicitly disclosed gap in each of their own write-ups. T23 is the first chance to close it with real, repeatable coverage instead of another manual pass.

## Decision

**k6 via the official Docker image, not a global binary install** — matches this repo's existing "run infra via Docker" convention (Postgres/Redis/MinIO/ClamAV already run this way), and avoids installing yet another global CLI tool. Targets `host.docker.internal` since core-api runs on the Windows host, not inside the compose network.

**Real access tokens for the load test are minted through the actual OTP login flow, not a fabricated bypass.** `get-tokens.sh` drives `request-otp` → reads the code directly out of Redis (the same manual check used by hand for every OTP verification since T02) → `verify-otp`, for every one of the 7 real seeded demo accounts (`database/seed/demo-data.ts`) — spreading load across genuinely distinct users' own throttle buckets rather than hammering one shared account's budget, or inventing accounts that don't exist.

**The load test found a real defect, not just a number: the global throttle (T22/ADR-0031) was keyed by raw IP, and that throttled `/health` itself under load.** A real uptime monitor polling `/health` from a shared or high-frequency source would see false "downtime" purely from the throttle — corrupting the exact metric this task exists to validate. Fixed with `@SkipThrottle()` — health checks must never be rate-limited, full stop.

**The deeper fix: `IdentityThrottlerGuard` keys authenticated requests by user id, not IP.** The same IP-keyed bucket that broke the load test (many requests, one source IP) is also a real production risk: any MEPMA office where several officials share one NAT gateway would collectively exhaust one shared bucket, throttling legitimate users who never individually did anything abusive. It decodes the bearer token itself (best-effort — falls back to IP on any decode failure, which covers "no token at all," i.e. every unauthenticated route) rather than waiting for `JwtAuthGuard` to populate `req.user`, because it must keep running _before_ `JwtAuthGuard` in the guard chain — T22's whole point was capping raw request volume regardless of auth outcome, so an invalid/expired-token flood must stay IP-throttled too, not get a free pass by failing auth first. Unauthenticated routes (`/auth/request-otp`, `/ondc/on_search`, etc.) are unaffected — they have no token to decode, so they keep the original IP-keyed behavior, which is exactly what OTP-request abuse prevention needs.

**Playwright drives the real two-step phone-OTP login end to end, including reading the real OTP out of Redis** — the same pattern the load test's token-minting script uses, and the same manual `docker exec redis-cli GET otp:code:<phone>` check used by hand throughout this whole project. No test-only login bypass exists or was added.

**Fixing the E2E harness itself mattered as much as fixing app bugs.** Two real races surfaced only once tests ran repeatedly: (1) `.click()` on "Send OTP"/"Verify" only waits for the click event, not the async request it triggers inside the React handler — reading Redis or hard-navigating immediately after intermittently raced ahead of the real network call. Fixed by waiting for the actual `waitForResponse()` plus (for verify) the post-login `waitForURL()`, not an arbitrary delay. (2) The original dashboards spec logged in fresh once per dashboard (6 times) for one shared demo account, real risk of exhausting `OTP_MAX_REQUESTS_PER_WINDOW=5/hour` on repeated runs — restructured to one login per describe block, which is also the more realistic scenario (one official session browsing several dashboards).

**Three dashboards had a real, repeated content bug Playwright's heading assertions caught by accident: reusing the page's own title text as the label for unrelated widgets.** `ShgDashboardPage`'s own SHG-count stat card, sales-by-SHG chart, and SHG-list table caption were all literally labeled "SHG Dashboard" (the page's own `<h1>` text) instead of anything describing what they actually show; `UlbDashboardPage` did the same and, when drilled into a specific ULB, borrowed _`shgDashboard.title`_ for its SHG-breakdown widgets instead of anything of its own; `GovernmentDashboardPage`'s districts-covered stat card was labeled "District Dashboard." Fixed with new, specific i18n keys (English + Telugu) per widget — `shgDashboard.totalShgs`/`salesChartTitle`/`listCaption`, `ulbDashboard.totalUlbs`/`listCaption`, `governmentDashboard.districtsCovered`. One instance (`ShgDashboardPage`'s chart title, rendered as an `<h3>` via `CardTitle`) also duplicated the page's own `<h1>` text exactly — a real accessibility/uniqueness problem, not just cosmetic, since a screen reader or a `getByRole('heading', {name})` query can no longer tell the two apart. Playwright specs were also tightened to assert on `level: 1` specifically, so this class of bug fails loudly again if it recurs.

**Voice-accuracy re-validation uses a genuinely new holdout set (`eval/holdout_utterances.py`), not a re-run of T11's own tuning set.** T11's 17 utterances are what `app/bot.py`'s system prompt and tool schemas were implicitly shaped around while being written — re-running them proves self-consistency, not generalization. 15 new utterances, same categories, same scoring shape, written without looking at the production prompt while writing them. Its STT-WER numbers were obtained (Sarvam API); its intent-routing numbers were not — this task's own re-runs against the tuning set used almost the shared Groq org's entire free-tier daily token quota (100,000 TPD) before the holdout set's turn came up, and the quota did not meaningfully free up across ~35 minutes of waiting through Groq's own quoted retry windows. Reported honestly as not obtained this session in `docs/eval/T23-stabilization-eval.md`, with the exact command to run it once quota allows, rather than a fabricated number.

**The eval tooling itself was broken and stale before either script could even run — found and fixed before trusting any number from it.** `run_intent_eval.py` imported `app.bot._SYSTEM_PROMPT`, which stopped existing once the prompt moved to `app.prompts.SYSTEM_PROMPT` after T11 — a plain `ImportError`, silently broken since whenever that refactor happened, unnoticed because these scripts aren't part of CI (by design — they cost real API money/time per T11's own ADR-0020). Separately, both scripts crash printing Telugu text on Windows because console/redirected-output defaults to cp1252, which can't encode it — fixed by reconfiguring stdout to UTF-8. And `test_utterances.py`'s ground truth for scheme-guidance queries still said "decline" (`None`) — true at T11, when no tool existed for it, but ADR-0021 added a real `scheme_guidance` RAG tool right after T11 and the test set was never updated, so it was penalizing objectively correct behavior. Fixed the labels rather than either leaving a misleading low accuracy number or quietly ignoring the mismatch.

**The malformed-tool-call issue ADR-0020 already found and characterized as stochastic is still real, and still not hardened in production — recorded as a higher-priority follow-up now, not fixed here.** Re-running the (corrected) tuning set multiple times in this task hit it on different utterances each time, confirming noise rather than a deterministic bug, and `retries=1` recovered to at/above the 90% target every time — the exact fix T11 already identified but never implemented in `app/bot.py`. Production calls Groq through Pipecat's `GroqLLMService`, a thin subclass of `BaseOpenAILLMService` whose actual completion/tool-call loop lives deep in the framework; adding a retry there means patching or subclassing internals this task had no safe way to test against a real live voice call (WebRTC audio, not the eval script's plain text) in the time available. Documented here as real, prioritized, tracked follow-up work instead of a rushed change to a live real-time pipeline.

## Real findings from verification

- k6: clean run at 0% error rate / 6.3ms avg response after the throttler fix (was 97% failure before it).
- Playwright: 12/12 passing on the final run, after fixing the two harness races and the OTP-rate-limit test-design issue described above.
- Voice accuracy: tuning set (corrected) 76.5% at retries=0, 94.1% at retries=1 — reproducing T11's own retries=1 number exactly. Holdout set numbers and the WER comparison are in `docs/eval/T23-stabilization-eval.md`.
- `npm run lint`/`test` clean across all Node packages after every fix in this task; core-api's new `IdentityThrottlerGuard` has its own unit tests covering the token-decode/fallback-to-IP/invalid-token paths.
- `turbo run lint test build` clean across every Node package (matching CI's Node job). `ruff`/`pytest` clean on voice-service (49/49) after the eval-script fixes. ml-services' pre-existing, already-documented (ADR-0030) Windows-clock-resolution flaky test is still the only non-green result anywhere in the repo, and still passes on Linux CI — not a regression from this task.

## Alternatives Considered

- **Reordering the global guard chain so `JwtAuthGuard` runs before the throttler**, so `req.user` is already populated when `getTracker()` runs — rejected; it would let an invalid/expired-token flood against a protected route bypass the throttle entirely (each request fails fast at auth before the throttler ever sees it), which is a real regression from what T22 built this control for. Decoding the token directly inside the throttler guard avoids that trade-off entirely.
- **Raising the global throttle's limit instead of re-keying it** — rejected; a higher IP-wide number doesn't fix the actual problem (one shared bucket for many distinct legitimate users), it just delays when it's hit.
- **Re-running T11's own test set and calling that the holdout re-validation** — rejected; it isn't a holdout if it's the exact set the system prompt was written against.
- **Patching Pipecat's `GroqLLMService`/`BaseOpenAILLMService` to add the retry-once policy in production** — rejected for this task; real-time voice pipeline internals from a third-party framework, no safe way to verify against an actual live call in the time available. Recorded as the top follow-up item instead.
- **Downgrading the throttler-keying finding (#2 in the eval report) to "won't fix"** — rejected; it's a real production-topology risk even though it hasn't been observed at this POC's actual scale, and the fix (identity-keying) was no more work than leaving it IP-keyed, so there was no reason not to fix it now that the load test surfaced it.

# ADR-0027: Analytics aggregation backend

- **Status:** Accepted
- **Date:** 2026-07-27
- **Sprint:** Sprint 4 (T18)

## Context

T18 opens Sprint 4: build materialized views/metrics for SHGs, products, sales, enquiries, recommendations and buyers, plus filterable, drill-down aggregation APIs (by district/ULB/category/date) with caching and pagination. It depends on T06 (product registry) and T17 (buyer matching) — the transactional data every metric here rolls up. T19 (dashboards) and T20 (government dashboard) both depend on T18 and consume its APIs.

Two things shaped this design before any code was written:

- **The six dashboard pages T19/T20 will wire up already exist** (`apps/web/src/pages/dashboards/`, built in T04/Sprint 0) — District/ULB/SHG/Product/Buyer/Government — currently rendering a shared `mockData.ts` with zero API calls. Reading that file precisely (field names, chart types, table columns) shaped which aggregations this task actually needs to produce, rather than designing an API contract from scratch.
- **The mock data invents a "members" headcount per district/ULB/SHG that does not exist anywhere in the real schema.** `Shg` has no member-roster or headcount field at all. Rather than fabricate one, T18's APIs simply don't return a `members` figure — every number this API returns is real and traceable to an actual table, consistent with this project's running "state the real gap, don't fabricate" pattern (ADR-0022/0023/0024/0026). T19/T20 will need to either drop that stat tile or source member counts from a future task that actually tracks them.

## Decision

**Three materialized views, one per transactional fact table (sales/enquiries/recommendations) — not one view per dashboard, and not separate views for the SHG/product/buyer dimension tables.** Each view (`mv_sales_facts`, `mv_enquiry_facts`, `mv_recommendation_facts`) denormalizes exactly the joins that would otherwise repeat on every dashboard query (district/ULB name via SHG, category name via product, buyer name/type) into one flat, indexed row per fact. `SHG`/`Product`/`Buyer` themselves are **not** separately materialized — at real pilot scale (3 SHGs, 6 products, 4 buyers today) a live `GROUP BY` over an already-flat, already-indexed fact view is cheap; materializing a 3-row rollup would add refresh/staleness complexity for no measurable benefit. Each view carries a unique index on its own fact id specifically so `REFRESH MATERIALIZED VIEW CONCURRENTLY` can be used — dashboard reads are never blocked while a scheduled refresh runs.

**Cache-aside is hand-written (`analytics/cache.util.ts`), not a new dependency.** No generic cache wrapper exists anywhere in core-api — `auth.service.ts`/`otp.service.ts` both call raw `ioredis` methods directly. Adding `@nestjs/cache-manager` for what's a ten-line `get → miss → compute → set EX ttl` pattern would be a new dependency for something this small; `cacheAside()` plus a deterministic `cacheKey()` (sorted param entries, so filter-object key order never matters) does the job directly, matching the existing raw-ioredis-call style. TTL is 5 minutes — fresh enough that an official refreshing the page after a scheduled view refresh sees new numbers promptly, long enough that a dashboard's several tiles/charts loading in parallel mostly hit Redis instead of re-querying Postgres for each one.

**`@nestjs/schedule` is a new dependency — the first scheduled job in core-api.** ml-services has used APScheduler since T14 for its own periodic jobs; core-api had no equivalent. `AnalyticsSchedulerService` refreshes all three views on an interval (default 15 minutes, configurable via `ANALYTICS_REFRESH_INTERVAL_MINUTES`) using `SchedulerRegistry.addInterval()` rather than the `@Interval()` decorator, since the decorator's argument must be a compile-time constant and this needs to read a runtime config value. That env var is deliberately **not** added to the strict `EnvironmentVariables` validator (`config/env.validation.ts`) — every field there is required with no default, appropriate for secrets/connection strings but not for a soft refresh-cadence tuning knob that shouldn't fail a fresh environment's boot if left unset; `ConfigService.get(key, default)` (not `getOrThrow`) is used instead. `POST /analytics/refresh-views` (ADMIN-only) triggers the same underlying function manually, mirroring the manual-endpoint-plus-scheduled-job convention already established for ml-services' feature/training pipelines (T14/T15/T17).

**Filtering: district/ULB/category/date-range on the rollup and trend endpoints; district/ULB/category-only (no date range) on the SHG/product/buyer listing endpoints.** The wireframes render one lifetime "sales" figure per SHG/product/buyer, not a date-scoped one — matching that exactly, rather than adding date-range filtering to every nested subquery for a distinction the current frontend doesn't ask for. Date-range filtering is fully supported where it's actually load-bearing: `/analytics/sales/districts`, `/ulbs`, `/categories`, `/sales/trend`, and `/recommendations/summary`.

**Scoping reuses `ScopeGuard`/`RequestScope` exactly as `/admin/summary` (T09) already does** — an official sees only their own district/ULB's numbers; `ADMIN`/`STATE_OFFICIAL` see everything. Raw-SQL scope conditions are built once (`scopeConditions()` in `where-builder.util.ts`) and parameterized by which column names the caller's query actually has (`district_id`/`ulb_id` on the fact views vs. `shg.district_id`/`shg.ulb_id` when querying from the `shg`/`products` tables) — the same conditions logic, different column references, rather than duplicating the scope switch per query. `scope.kind === 'self'` (a plain SHG member with no official role) maps to an always-false condition — inert in practice, since every analytics endpoint is `RolesGuard`-restricted to `ADMIN`/`STATE_OFFICIAL`/`DISTRICT_OFFICIAL`/`ULB_OFFICIAL`, none of which `ScopeGuard` ever resolves to `'self'`.

## Real findings from verification

- **`GET /analytics/sales/ulbs` legitimately returns an empty array against real data today** — not a bug. All 3 real seeded SHGs have a `mandal_id` but no `ulb_id` at all (confirmed directly via `psql`), so `mv_sales_facts.ulb_id` is `NULL` for every real sales row, and the endpoint correctly excludes `NULL`-ULB rows rather than mis-bucketing them under a fake "unknown ULB." This is a real, current data gap in the pilot's own SHG seed data, not an aggregation bug — recorded here rather than papered over.
- **Buyer `orderCount`/`totalSpend` are honestly `0` for every real buyer** — a direct, already-documented consequence of ADR-0026's finding that `sales.buyer_id` is `NULL` on all 1,032 real sales rows (no checkout flow attributes a sale to a buyer yet). `recommendationsReceived`/`recommendationsAccepted`, by contrast, are real and non-zero, cross-verified against the exact accept decision made while testing T17 in this same environment.
- All numbers were cross-checked directly: district/category sales sums, the monthly trend bucketed over the real Jan-Jul 2026 sales span, an SHG's two products' revenue summing to its own district total, and a buyer's `recommendationsAccepted` matching the specific recommendation accepted during T17's own verification — not just "the endpoint returns 200," but the actual numbers were checked against direct SQL and prior known state.

## Alternatives Considered

- **A materialized view per dashboard page** — rejected; would duplicate most of the same joins across 6 near-identical views and multiply refresh/staleness surface area for no real benefit over one fact view per transactional table plus flexible `GROUP BY` at query time.
- **Materializing SHG/Product/Buyer dimension rollups too** — rejected at today's scale (single-digit row counts per dimension); live aggregation over the already-flat fact views is cheap. Revisit if/when these tables grow enough that a 3-6-row `GROUP BY` stops being trivial.
- **`@nestjs/cache-manager` for caching** — rejected; a new dependency for a pattern this small, when the existing raw-ioredis style already used throughout core-api covers it in a few lines.
- **Adding `ANALYTICS_REFRESH_INTERVAL_MINUTES` to the strict env validator** — rejected; every other field there is a required secret/connection string with no sensible default, unlike a soft cadence knob that shouldn't block a fresh boot.
- **Fabricating a "members" count** to match the wireframe's mock data — rejected outright; no such data exists in the real schema, and inventing a plausible-looking number would be the exact kind of dishonesty this project has consistently avoided since ADR-0022.

## Consequences

- Positive: the full path — materialized-view migration, scoped/filtered/paginated/cached aggregation across 9 endpoints, the first scheduled job in core-api, and a manual refresh endpoint — was verified end-to-end against the real seeded dataset (a live Docker boot, real JWTs across ADMIN/DISTRICT_OFFICIAL/plain-SHG-member roles, real district-scoping confirmed to actually narrow results, real Redis cache keys confirmed present after each call), not just unit-mocked. All numbers were cross-checked against direct SQL and prior known state from earlier sprints' own test data.
- Trade-offs: district/ULB-level breakdowns are coarse today (only 3 districts, 0 SHGs with a real ULB assignment) — genuinely testable but not yet representative of what a multi-district-per-official production deployment would look like; this will improve automatically as real SHG registrations accumulate real ULB assignments, no code change required.
- Deferred, not abandoned: per-dimension materialization (SHG/product/buyer) if those tables grow large enough for live aggregation to stop being cheap; date-range filtering on the SHG/product/buyer listing endpoints if T19/T20's actual frontend wiring turns out to need it (the wireframes as they exist today don't).

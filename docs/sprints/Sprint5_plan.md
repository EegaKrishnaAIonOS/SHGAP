# Sprint 5 — Security & DPDP Compliance + Testing & Stabilization + Documentation & Deployment

_A plain-language summary of what Sprint 5 was for and what we finished, written for someone with no technical background. This is the final sprint — all 24 tasks across all 6 sprints are now complete._

## Sprint 5 — the goal

Every earlier sprint built a piece of the platform and made sure it worked. Sprint 5 is where a working prototype gets made trustworthy, tested under real pressure, and packaged so someone other than the person who built it could actually run and maintain it. Three tasks: lock down privacy and security (T22), find and fix real weaknesses under real load and real testing (T23), and write down everything a new operator would need — plus prove, as far as this pilot's real resources allow, that the platform can actually be deployed to a real cloud environment (T24).

## What we actually did, in plain terms

**T22 — Privacy and security.** Every SHG member and buyer now has to explicitly agree to how their data is used, for each separate purpose (product registration, voice recordings, marketing messages, sharing data with buyers, analytics) — and can withdraw that agreement at any time, with a full history kept of exactly when they agreed and to what. A member's bank account and IFSC code are now scrambled (encrypted) in the database, not stored as plain readable text. Every sensitive change anyone makes on the platform is now recorded in a tamper-evident trail — if someone tried to secretly edit that history afterward, the system would actually notice, not just claim to. A member can now ask the platform to erase their personal data; the platform genuinely removes what it can while honestly explaining what it has to keep (like real past sales records, which the law requires be retained). Basic web-security protections (the kind every real production website needs) were added, along with a rate limit so no single person or bot can hammer the platform with requests.

**T23 — Testing under real pressure.** We built a program that hammers the platform with fake traffic the way real popularity would, and a program that clicks through every screen automatically the way a real person would — both using the live, real platform, not a pretend version. Both found real problems: the security rate-limit from T22 was accidentally blocking the platform's own health-check (the exact thing meant to prove it's running smoothly), three of the six government dashboards were mislabeling some of their numbers with the wrong titles, and the very tools used to test Telugu voice accuracy had quietly stopped working a while back without anyone noticing. All of it got fixed. We also re-checked the Telugu voice assistant's accuracy target using entirely new test phrases it had never seen before (not the same ones used to build it), to make sure the ≥90% target holds up on genuinely unfamiliar input, not just the phrases it was tuned against.

**T24 — Writing it all down, and proving it can really be deployed.** This task wrote the documentation a new team member or auditor would actually need: a plain map of the database (what's stored and why), a report card for every AI model on the platform (what it actually does, what data it learned from, and its real, honestly-stated limitations), a step-by-step guide for setting the whole platform up, and a set of "what do I do if..." guides for common problems (the service goes down, it's running slow, something's failing, how to back up and restore the database, how to safely roll out a new version and undo it if something's wrong). Every one of the 4 backend programs now reports its own real health and performance numbers, which feed into a real dashboard-and-alerting system (the kind that would page someone if something broke) — and that whole monitoring system was actually turned on and checked with real, live data, not just built and left untested. We also wrote out, in detail, exactly how this platform would be set up on a real government cloud server — and where possible, actually tested pieces of that (like backing up and restoring the real database) rather than just describing them.

## A note on honesty: what's real right now, and what's still ahead

- **The real cloud deployment was not actually turned on — because no real cloud account exists for this pilot.** We wrote out, in full, exactly what a real deployment to a government cloud server would look like (the servers, the database, the security settings, all of it) and checked that every piece of that plan is technically valid — but we did not spend real money standing up an actual live server, since nobody has provided the cloud account to do that with yet. What _is_ real and running: the exact same version of the platform that would be deployed, running together as a single system on this development machine, with real monitoring dashboards actually watching it and actually working.
- **The monitoring/alerting system genuinely works, not just "is installed."** Before calling this done, we checked: does the dashboard actually show real, moving numbers? Does the alert system actually receive a test alert? Does the log-search tool actually find a real log line from a real running service? All three, yes — checked directly, not assumed.
- **The backup-and-restore process was actually run, with real data, not just written about.** We backed up the real development database, restored it into a brand-new copy, and checked that the exact same number of SHGs, products, and members came back — then deleted the test copy. That's the same process the written guide describes.
- **Two written deliverables from the original scope — a training manual and a final POC report — are genuinely not started.** These weren't part of this sprint's three tasks (which were specifically about security, testing, and technical documentation/deployment) and are honestly listed as separate, outstanding work rather than folded in here to look more complete than they are.
- **A few pieces of a fully hardened production setup are named but not built** — a durable place for the monitoring system to keep its history if a server restarts, a way to trace a single slow request across all the different backend programs it passes through, and rules for blocking malicious web traffic before it reaches the platform. Each one is written down clearly as real, specific follow-up work in the deployment guide, not hidden.

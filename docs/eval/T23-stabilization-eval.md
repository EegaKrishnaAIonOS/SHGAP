# T23 evaluation report — load test, E2E, voice-accuracy re-validation, defect triage

- **Date:** 2026-07-31
- **Sprint:** Sprint 5 (T23)
- **See also:** ADR-0032, ADR-0020/T11-nlu-eval.md (original voice-accuracy baseline), ADR-0031 (the throttler this task found a real gap in)

## Load test (k6, `apps/core-api/test/load/`)

Real k6 (official `grafana/k6` Docker image, targeting `host.docker.internal`) against a live core-api + Postgres + Redis + notification-service, using real access tokens minted through the actual phone-OTP login flow (`get-tokens.sh` — request-otp, read the code straight out of Redis, verify-otp; no bypass endpoint exists or was added). Three scenarios: `health_check` (unauthenticated, high concurrency), `authenticated_reads` (7 VUs — one per real seeded demo account, so each has its own throttle bucket rather than several VUs sharing one — hitting `/analytics/*`, `/master-data/categories`, `/shgs`), `otp_request_only` (3 VUs, synthetic phones, paced to respect the shared IP-keyed bucket unauthenticated traffic uses).

**First run surfaced a real defect, not a benign result:** 97% of requests failed. Root cause: the global anti-abuse throttle added in T22 (100 req/min, keyed by raw IP) throttled the `/health` endpoint itself along with everything else — a real uptime monitor polling it would see false "downtime" purely from the load, undermining the exact `>=99% uptime` metric this task exists to validate. Fixed (see ADR-0032) and re-run clean:

| Metric                  | Result                                        |
| ----------------------- | --------------------------------------------- |
| `http_req_duration` avg | 6.3ms (target: <3000ms)                       |
| `http_req_failed` rate  | 0.00% (target: <1%, used as the uptime proxy) |
| Total requests          | 2,355 over ~71s, 100% success after the fix   |

## End-to-end tests (Playwright, `apps/web/e2e/`)

Real Chromium against the live Vite dev server + live core-api, no mocked network calls — including a fully-automated real phone-OTP login (reads the OTP straight out of Redis, same as the load test's token-minting script) rather than a test-only bypass. Covers: home page, login (real OTP round trip, wrong-OTP rejection, change-number, protected-route redirect-and-back), SHG registration (brand-new phone number → first login → 4-step registration → real `Shg` row created), product catalogue (real seeded products, search filter), all 6 official dashboards (real data, RBAC — an SHG member is confirmed blocked, not silently redirected), and the admin portal (tab visibility + direct-URL RBAC for the ADMIN-only Master Data page).

**12/12 passing** on the final run, after fixing two real bugs the first runs surfaced (see "Defect triage" below, #3 and #4): a race in the test helper itself (worth fixing even though it's not an app bug — a flaky harness is as useless as no harness) and a real product content bug across three dashboards.

This also closes a standing gap from T19-T22: no browser-automation tool existed then, so those tasks' UI changes were verified only by hand. This is the first task with real, repeatable, automated browser coverage of the whole app.

## Voice-accuracy re-validation (`apps/voice-service/eval/`)

T11's own test set (`test_utterances.py`, 17 utterances) is what the system was implicitly shaped around while `app/bot.py`'s prompt and tools were being written — a clean re-run of it isn't a real holdout check. `holdout_utterances.py` (15 new utterances, same categories, same `{text, language, expected_tool}` shape, never used while writing any of the production code) is the actual holdout set this task's "re-validate on a holdout set" deliverable calls for.

**Real, unrelated defect found in the eval tooling before either could even run**: `run_intent_eval.py` imported `app.bot._SYSTEM_PROMPT`, which stopped existing when the prompt was refactored into `app.prompts.SYSTEM_PROMPT` at some point after T11 — the script has been silently broken (an `ImportError`) since then. Fixed. Separately, both eval scripts crash printing Telugu text to a non-UTF-8 stdout (Windows' console/redirected-output default is cp1252) — fixed by reconfiguring stdout to UTF-8.

**Real, stale ground truth found**: `test_utterances.py` still expected `None` (decline) for scheme-guidance questions — correct at T11, when no such tool existed, but ADR-0021 (Sprint 2, right after T11) added a real `scheme_guidance` RAG tool. Fixed the expected labels to `scheme_guidance` rather than silently accepting a wrong-looking accuracy number for what is now correct behavior.

### Intent-routing accuracy (real Groq API calls)

| Dataset                    | Retries | Accuracy                  | vs. target       |
| -------------------------- | ------- | ------------------------- | ---------------- |
| Tuning set (17, corrected) | 0       | 13/17 = 76.5%             | below 90%        |
| Tuning set (17, corrected) | 1       | 16/17 = 94.1%             | **at/above 90%** |
| Holdout set (15, new)      | 0/1     | not obtained this session | see note below   |

The retries=1 tuning-set result (94.1%) matches T11's own original retries=1 result exactly, on a corrected label set — a genuine reproduction, not a fluke.

**Real, honest limitation — not a fabricated number:** the holdout-set intent-routing run could not complete in this session. The re-runs above (tuning set, both retry settings, re-run several times while fixing the stale-import/encoding/ground-truth bugs) used almost this org's entire real Groq free-tier daily token quota (100,000 TPD); every subsequent attempt at the holdout set hit `groq.RateLimitError: ... tokens per day (TPD): Limit 100000, Used ~99,600-99,700`, and waiting through three of Groq's own quoted retry windows (roughly 35 minutes total) did not meaningfully free up capacity — it's a daily-boundary reset, not the short rolling window the error message's "try again in Nm" phrasing implies. Rather than wait indefinitely or report a made-up number, this is the honest state: the holdout set exists, is wired into both eval scripts (`python eval/run_intent_eval.py <retries> holdout`), and should be run once the daily quota resets (or against a paid Groq tier) — real follow-up work, not skipped scope. **The holdout set's STT WER numbers (below) were obtained** — Sarvam is a separate API/quota, unaffected by this.

**The malformed-tool-call failure mode ADR-0020 already characterized as stochastic is still real and still not hardened in production.** Across the re-runs in this task, it hit multiple different utterances on different runs (not one specific input every time), confirming it's noise in Groq's tool-call generation, not a deterministic prompt/schema defect — the same conclusion T11 reached, now with more evidence of how often it actually bites (roughly 1 in 4-5 calls at retries=0 in these re-runs). **`retries=1` recovers to at/above the 90% target every time it was tried in this task** — the same fix T11 already identified. It remains implemented only in the eval script, not in `app/bot.py`'s production pipeline. Production uses Pipecat's `GroqLLMService` (a thin wrapper over `BaseOpenAILLMService`'s internal completion/tool-call handling) — adding a retry there means patching or subclassing deep framework internals this task did not have a safe way to test against a live voice call (WebRTC audio, not just text) in the time available. Recorded here as a real, higher-priority-than-T11-realized follow-up, not attempted as a rushed fix to real-time pipeline internals — see ADR-0032.

### STT word-error-rate (real Sarvam TTS→STT round trip)

| Dataset                                            | Telugu norm. WER | English norm. WER |
| -------------------------------------------------- | ---------------- | ----------------- |
| Tuning set (T11's own numbers, reproduced exactly) | 0.123 (n=9)      | 0.169 (n=8)       |
| Holdout set (new)                                  | 0.142 (n=8)      | 0.145 (n=7)       |

Same methodology caveat as T11: this is Sarvam's own TTS→STT pair agreeing with itself, not real human speech — a floor on real-world WER, not an estimate of it. The holdout numbers are close to the tuning-set numbers (no cherry-picking/overfitting artifact from the original test set having been iterated against), and Telugu's normalized WER improves relative to English in both sets, consistent with T11's finding of no systematic Telugu-specific weakness in Sarvam's engine itself.
